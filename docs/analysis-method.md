# 分析方法与验证

本文说明：**这些文档里的结论是怎么得到的、经过什么验证、以及哪些东西没有公开。**

分两部分看：

1. **第一阶段**：手里只有打包好的可执行文件，没有源码 → 做结构性还原
2. **第二阶段**：拿到源码 → **回头验证第一阶段的结论**

第二阶段才是本文的重点：它把「我推断出了什么」变成了「我推断的准不准」。

---

## 一、第一阶段：只有二进制时做了什么

### 起点

| 有 | 没有 |
|---|---|
| 一个 Windows 可执行程序（约 3.7 MB） | ❌ 源代码 |
| 旁边的运行时目录（约 125 MB） | ❌ 开发记录 / 提交历史 |
| 一份使用说明 | ❌ 原始测试套件 |
| 业务资料（母版 + 产品资料） | ❌ 设计文档 |

程序是 **PyInstaller 打包产物**（onedir 布局）。这类产物**不含 Python 源码**——源码被编译成字节码后塞进归档。

### 步骤

**1. 确认打包形态**

从归档元信息读出：PyInstaller v21、Python 3.13、**未加密**、CArchive 12 个条目、PYZ 归档存在、入口脚本 `launcher`。

「未加密」是关键判断——加密产物需要运行时密钥，分析路径完全不同。

**2. 解包**

用 `pyinstxtractor-ng` 解出 CArchive 与 PYZ，得到 4 个应用模块和数百个依赖模块。

**3. 用同版本解释器还原结构**

> **版本对齐是硬约束。** 字节码的 marshal 格式与解释器小版本绑定。本机运行时是 3.12，目标是 3.13——**3.12 根本读不了** 3.13 的 `.pyc`。

于是下载 **CPython 3.13 embeddable**（11 MB）来做 `marshal.loads`。

这一步的产出是**确定性的**，不含推测：

| 拿到 | 说明 |
|---|---|
| 模块文档 | PyInstaller **保留 docstring**，模块职责原文可读 |
| 函数/类定义 | 名称、行号、参数签名 |
| 函数文档 | 每个函数的 docstring |
| **全部字符串常量** | 选择器、配置键、提示文案、错误信息、路径 |
| 反汇编 | `pycdas` 得到 14,000+ 行 |

**4. 交叉验证**

同一事实尽量多个来源印证。例如「工具只读」：模块文档写明不点哪些按钮 + 字符串常量有「全程只读…未绕过供应商权限」的结论行 + 反汇编中无提交类请求构造。

### 完整源码没拿到（当时）

试过并记录在案的路径：

| 工具 | 结果 |
|---|---|
| **REA**（`morluto/rea`，17 万星） | ❌ 其 24 类目标中**没有 Python 字节码**；最接近的「原生二进制」只能分析 PyInstaller 的 C 引导程序，「进程行为」要求 Linux/macOS PTY |
| **pycdc**（预编译） | ❌ `Unsupported opcode: MAKE_FUNCTION (122)`——3.13 的函数体解不出来 |
| **pychd**（「混合规则 + LLM」） | ❌ **主动排除**：读其源码发现它不做反编译，而是把 `dis` 结果发给 LLM 让模型**写出**源码。这属于生成而非还原，产出会是编造的代码 |
| **pylingual**（学术界，支持 3.6–3.15） | ⚠️ 未跑通：依赖 `torch` + `transformers` + HuggingFace 模型（GB 级）；`uv` 缓存目录被拒绝访问 |
| **PYC-Decompiler.exe** | ⚠️ 无命令行输出，疑似 GUI，未采用 |

**为什么 3.13 特别难**：反编译器对 Python 版本的支持是滞后的——`uncompyle6`/`decompyle3` 到 3.8，`pycdc` 到 3.12 且 3.13 仍缺 opcode。`.pyc` 里每个 opcode 都要在反编译器里显式实现，`MAKE_FUNCTION` 这类核心指令没实现，函数体就整段解不出来。

> 排除 `pychd` 是这一阶段最有价值的一个动作。一个名字里带 "decompiler" 的包，实际做的事可能是让大模型编代码——用它产出的「源码」会污染全部结论。

## 二、第二阶段：拿到源码后的验证

后来从原开发者处取得了源码包。它带来两个用处：**验证**与**纠偏**。

### 验证：模块与函数级别

把源码用 `ast` 解析出全部定义，与第一阶段从字节码还原的结果逐项比对：

| 模块 | 字节码还原 | 源码定义 | 吻合 |
|---|---:|---:|---:|
| `app_paths.py` | 7 | 7 | **100%** |
| `launcher.py` | 2 | 2 | **100%** |
| `collector.py` | 20 | 20 | **100%** |
| `statement_engine.py` | 22 | 22 | **100%** |
| **合计** | **51** | **51** | **100%** |

差集只有 `<lambda>` 与 `<genexpr>`——那是推导式/匿名函数在字节码里生成的匿名代码对象，源码里本来就不是 `def`，属于正常差异而非遗漏。

**结论：模块划分与函数清单的还原是完全准确的。**

### 更细的一层：版本漂移

逐函数比对**行号**后，发现了一件更精确的事：

| 模块 | 行号一致 | 结论 |
|---|---|---|
| `statement_engine.py` | 20 / 20 | 与打包产物同一修订版 |
| `launcher.py` | 2 / 2 | 同一修订版 |
| `app_paths.py` | 7 / 7 | 同一修订版 |
| `collector.py` | **13 / 19** | **不是同一修订版** |

`collector.py` 的 6 个函数行号全部**偏移 −24 行**，而插入点之前的 13 个函数行号完全一致；同时源码里多出一个字节码中没有的函数 `ensure_child_visible`。

也就是说：

```
源码比打包产物新 —— 在打包之后（约 2 小时的间隔内）新增了 ensure_child_visible（正好 24 行）
```

**13 个未偏移 + 6 个偏移 −24 + 1 个仅源码有**——三个数字互相自洽，这不是巧合能解释的。

这个发现的价值不在于「发现了 bug」，而在于：**它能被证伪。** 如果分析是模糊的、靠猜的，就不可能得出一个精确到「24 行」且三处自洽的结论。

### 纠偏：补上了原来推不出的东西

源码也修正/补充了第一阶段的结论：

| 项 | 第一阶段 | 源码确认 |
|---|---|---|
| `ensure_child_visible` | 未还原出（因为它不在打包产物里） | 真实存在，且是核心处理 |
| ExtJS 展开图标语义 | 只知「点击展开图标」 | **是 toggle 而非 set**，误点会收起已展开的节点 |
| 同名按钮处理 | 从字符串常量推出「只点可见的」 | 实现确认，且有多套选择器降级 |
| 打包模式 | 从元信息推出 onedir | PyInstaller spec 文件确认 |

这几条现在写进了 [code-notes.md](code-notes.md) 与 [architecture.md](architecture.md)。

## 四、这篇文档想说明的方法论

1. **先确认工具形态再选方法。** 加密与未加密、onedir 与 onefile、3.12 与 3.13，路径完全不同。
2. **版本对齐是硬约束。** 用错解释器读字节码不是「结果不准」，而是**根本读不出**。
3. **优先取确定性证据。** 模块文档、字符串常量、函数签名都是字节码里的事实。先把这些拿干净。
4. **验证你使用的工具。** `pychd` 的例子说明：会用 LLM 编代码的工具，产出的「源码」会污染全部结论。
5. **拿到 ground truth 后回头对账。** 只有对账，才能把「我推断」变成「我推断得准不准」——并且能发现版本漂移这种靠猜得不到的细节。
6. **把边界写出来。** 「没拿到源码」和「拿到了但不完整」是两个说法，读者有权知道是哪个。
