# 架构

本文说明工具由哪些部分组成、每部分的职责边界，以及**这些结论是怎么得到的**。

## 证据来源说明（先读这段）

本文的结论**并非全部来自同一来源**，请按下面的标记区分：

| 来源 | 覆盖范围 | 可靠度 |
|---|---|---|
| **【字节码】** | 模块划分、函数名与签名、模块/函数文档、字符串常量 | 确定性事实（从打包产物直接读出） |
| **【源码】** | 函数实现细节、ExtJS 处理逻辑、配置项语义 | 确定性事实（有原始源码） |
| **【推断】** | 少数未在任一处显式写明的因果关系 | 推断，已标注 |

**一个重要前提**：源码与打包产物**不是同一修订版**。

比对结果为——`app_paths.py`、`launcher.py`、`statement_engine.py` 三个模块的行号与打包产物**完全一致**；
但 `collector.py` 中 13 个函数行号一致，另 6 个**统一偏移 −24 行**，且源码多出一个打包产物中没有的
`ensure_child_visible` 函数。也就是说：**打包之后，源码又新增了一个正好占 24 行的函数。**

因此本文描述的是**源码版的实现**；若你分析的是那个具体的 EXE，它在 `collector.py` 中缺少
`ensure_child_visible`，菜单展开的处理会不同。完整比对过程见 [analysis-method.md](analysis-method.md)。

## 全景

工具是一个**本地运行的单机程序**，没有服务端、没有数据库、不联网（除 ERP 本身）。

```
                    ┌─────────────────────────────────────────┐
                    │            launcher.py                  │
                    │  入口编排：自检 → 选账号 → 采集 → 生成   │
                    └───────────────┬─────────────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
   ┌──────────────────────┐                  ┌──────────────────────────┐
   │   collector.py       │                  │  statement_engine.py     │
   │   只读采集           │  CSV / JSON      │  确定性生成              │
   │   Playwright + Edge  │ ───────────────▶ │  openpyxl + 母版         │
   │   + PowerShell 弹窗  │                  │                          │
   └──────────┬───────────┘                  └────────────┬─────────────┘
              │                                           │
              ▼                                           ▼
      ERP 网页（客户系统）                      对账单 .xlsx + 报告 .json
        【只读，不改任何数据】                    （写入「成品」目录）
              │
   ┌──────────┴───────────┐
   │    app_paths.py      │  统一路径解析：按程序自身位置，绝不用 cwd
   └──────────────────────┘
```

## 模块职责

### `launcher.py` — 入口编排

| 项 | 内容 |
|---|---|
| 职责 | 串起整个流程，处理命令行参数与失败提示 |
| 主要函数 | `_selftest()`、`main(argv)` |
| 命令行参数 | `--selftest`、`--account`、`--outdir`、`--csv` |
| 自检内容 | Playwright 驱动是否可用、系统 Edge 能否找到、账号配置是否可读、资料目录是否可读 |

自检会在正式跑之前**先把环境问题暴露出来**，而不是等采集到一半才失败。它明确指出：Playwright 驱动异常时会打印异常原因，找不到系统 Edge 时给出回退警告。

`main()` 的返回值语义是 `0 = 成功 / 非 0 = 失败`，并且**不调用 `sys.exit`**——这样它可以被上层复用而不中断进程。

流程中的两阶段提示：

```
[1/2] 开始采集 <账号> 当月送货单 ...
[2/2] 开始生成对账单 ...
完成！对账单在：<路径>
```

失败时也有对应的明确文案（"数据采集未成功，请查看日志后重试"／"对账单生成未成功，请查看日志窗口"），不会静默退出。

### `collector.py` — 只读采集 【字节码 + 源码】

职责原文（模块文档）【字节码】：

> 选择账号 -> 打开 Edge（持久化 Profile）-> 检测/等待登录 ->
> 产品 -> 供应商平台 -> 供应商送货单 -> 列表 -> 查询 ->
> 翻页读取全部记录 -> 输出 CSV/JSON + 采集报告

安全约束原文（模块文档）：

> - 只读。不点击"确认对账/取消对账/金额对账/取消金额对账/导出Excel"等任何业务按钮；
> - 不保存、修改、提交、确认、取消任何 ERP 单据；
> - 不绕过供应商权限；
> - 账号密码不写入本程序（登录由人工在浏览器完成，状态存于本地 Profile）。

关键函数（按调用顺序）【字节码给出名称与签名，源码确认行为】：

| 函数 | 作用 |
|---|---|
| `choose_account(accounts)` | 置顶弹窗选账号；点 X 取消则退出。弹窗不可用时回退控制台选择 |
| `_find_edge_executable()` | 按标准安装路径 + 注册表 `App Paths\msedge.exe` 查找系统 Edge |
| `alert(title, message)` | 置顶信息弹窗，**阻塞**到用户点确定（用于人工登录环节） |
| `needs_login(page)` | 判断当前是否停在登录页 |
| `find_main_page(ctx)` | 在已打开页面里找主界面（以页面上一个固定的界面元素为准，而不是 URL 或标题） |
| `wait_login(ctx, timeout)` | 轮询所有页面，任一出现主界面即返回；超时返回 `None` |
| `ensure_child_visible(page, parent, child)` | **确保**父节点已展开且子节点可见（ExtJS 展开图标是切换语义，见下） |
| `expand_menu_node(page, name)` | 展开 ExtJS 树节点（点该行内的展开图标） |
| `click_menu_node(page, name, timeout)` | 点 ExtJS 树节点文字（叶子节点直接打开工作区） |
| `click_ext_button(page, text, desc, timeout)` | 点 ExtJS 工具栏按钮，**只点可见的那个** |
| `wait_for_data(page, timeout)` | 等数据加载完成 |
| `collect(page, month_start_iso)` | 翻页读取全部记录（含终止条件与去重） |
| `write_outputs(...)` | 写 CSV/JSON 与采集报告 |
| `_save_login_state(ctx, profile_dir)` | 登录成功后备份 Cookie + localStorage |

**ExtJS 展开图标是「切换」而不是「展开」** —— 这是整个采集器里最关键的一个坑，也是 `ensure_child_visible` 存在的原因。

若父节点本来就处于展开态，再点一下 expander 会把它**收起**，导致子节点消失、后续点击全部超时。
所以判据不能是「点击有没有报错」，而必须是「**子节点是否真的可见**」——检查后置条件，而不是动作返回值。

这个函数的实现、以及为什么这样写，见 [code-notes.md](code-notes.md)。

**为什么用 PowerShell 做弹窗**：`_run_ps(script)` 以 UTF-8 BOM 编码执行 PowerShell 脚本并取回 stdout；账号选择窗与信息弹窗都是用 `System.Windows.Forms` 现场拼出来的。这样做的好处是不给主程序引入 GUI 框架依赖（打包体积与兼容性），代价是弹窗样式由脚本决定。

**登录状态的双保险**：正常情况下 Playwright 的持久化 Profile 已经把 Cookie 存到磁盘；`_save_login_state` 额外把 `storage_state.json`（Cookie + localStorage）备份一份。备份失败是**可忽略**的（注释原文："备份登录状态失败(可忽略)"），不影响主流程。

### `statement_engine.py` — 确定性生成

职责原文（模块文档）：

> 对账单生成引擎（第三阶段）
> 输入: 采集器输出的 当前月份记录.csv
> 输出: YYYY年M月对账单.xlsx + statement_report.json

关键函数：

| 函数 | 作用 |
|---|---|
| `detect_desktop()` | 尽力定位真实桌面目录（兼容 OneDrive 重定向） |
| `resolve_resource_dir()` / `_find_template_in(d)` | 定位资料目录与母版文件（文件名含「母版」） |
| `load_csv(csv_path)` | 读采集输出 |
| `_norm_header(v)` | 表头文本规范化：去空白、括号统一、小写 |
| `norm_code(v)` | **料号规范化**：Excel 常把纯数字料号存成 float，还原成整数字符串 |
| `norm_price(v)` | 单价规范化；无法解析返回 `None`（后续按「缺金额填 0」规则处理） |
| `_detect_header(ws, scan_rows)` | 在前 N 行定位表头行，返回 `(行号, {字段: 列号})` |
| `_read_one_sheet(...)` | 解析单个工作表的产品资料行 |
| `load_product_master_dir(res_dir)` | 扫描资料目录下所有 Excel（母版除外），合并成产品资料字典 |
| `match_products(deduped, product_master)` | 料号为主键，**规格交叉验证**，名称辅助验证（仅提示不阻断） |
| `build_ledger(deduped)` | 按「单据日期 + 料号」汇总数量，返回账本与升序月份 |
| `_insert_date_cols(...)` | 插入 N 个日期列并复制母版日期列样式 |
| `build_workbook(...)` | 复制母版 → 写标题/日期/产品/公式 → 返回工作簿与缺单价清单 |
| `run_qa(...)` | 质检，每个检查项带 `fatal` 标记 |
| `main(argv)` | 返回 `0/非 0`，同样不调用 `sys.exit` |

设计上值得注意的三点：

1. **配置驱动母版坐标**。模板的行列位置（标题行、日期表头行、数据起止行、各列的列号、扣减/未税/税额/含税的偏移量）全部来自配置，代码里不写死具体行列。客户调整表结构时改配置而非改代码。
2. **质检内建**。`run_qa` 的检查项覆盖数量守恒、合计一致、料号覆盖等，并且区分 `fatal` 与 非`fatal`——fatal 不过就整体失败。
3. **失败要响**。料号在产品资料里找不到时是**明确异常**，模块文档原文写着「不允许猜, FINAL=FAIL」。

### `app_paths.py` — 统一路径解析

模块文档原文：

> 关键：所有目录都相对「程序本体所在位置」解析，**绝不使用 os.getcwd()**。
> 这样无论从命令行、资源管理器双击、还是桌面快捷方式启动，定位结果都一致
> （快捷方式的"起始位置"可能被设成别处，用 cwd 会找不到资料目录）。
> 打包后 sys.frozen 为真，此时以 exe 所在目录为根；源码运行时以脚本目录为根。

提供的目录：

| 函数 | 目录 | 用途 |
|---|---|---|
| `app_dir()` | 程序本体所在目录 | 打包后 = exe 所在目录 |
| `resource_dir()` | `对账资料\` | 母版 + 产品基础资料（账号共用一套） |
| `finished_dir()` | `成品\` | 最终对账单 |
| `work_dir()` | `output\<账号id>\` | 中间产物（CSV / JSON / 校验报告） |
| `profiles_dir()` | `profiles\<账号id>\` | 浏览器登录状态 |
| `ensure_dirs()` | — | 首次运行建出所需目录 |

这是被真实用户操作逼出来的设计：快捷方式的「起始位置」可以被设成任何地方，用 `cwd` 定位资料目录会失败。

## 数据流

```
ERP 网页
   │  （Playwright 只读采集）
   ▼
当前月份记录.csv  ──┐
                    │  statement_engine 读入
产品基础资料.xlsx ──┤
标准母版.xlsx ──────┘
                    │
                    ▼
            对账单 .xlsx（写入「成品\」）
            statement_report.json（质检结论 + 缺单价清单）
```

中间产物落在 `output\<账号id>\`，登录状态落在 `profiles\<账号id>\`——按账号隔离，两个账号互不干扰。

## 技术选型与实际约束

| 选择 | 说明 |
|---|---|
| Playwright + 系统 Edge | 用系统 Edge 而不是 Playwright 自带 Chromium，是为了贴近用户真实浏览器环境，避免被 ERP 判定为异常客户端；`_find_edge_executable` 显式指定 `executable_path`，注释原文说明目的是「确保 100% 用系统 Edge，杜绝回退到 Playwright…」【字节码注释】 |
| 持久化 Profile | 免登录体验；登录由人工完成一次，状态存本地【字节码 + 源码】 |
| openpyxl | 需要保留母版的样式与公式，纯数据写入库不够用【推断：由「需要公式与样式」这组事实推得，源码未显式说明选型理由】 |
| PowerShell 弹窗 | 避免为主程序引入 GUI 依赖【推断：同上，源码未写明理由】 |
| 单机、无服务端 | 部署就是拷一个文件夹【字节码：路径解析与目录结构】 |

> 标【推断】的两条是**设计动机**层面的解释，不是代码里写明的事实。工具确实使用 openpyxl 与
> PowerShell 弹窗（这是事实），但「为什么这样选」是我的合理推断。

## 与 ERP 的边界

必须说清楚的一点：这个工具**只读**。

- 采集阶段只做「导航 + 查询 + 翻页 + 读表格文本」
- 代码中明确列出**不点击**的按钮：确认对账、取消对账、金额对账、取消金额对账、导出 Excel
- 程序不提交、不修改、不删除任何单据
- 不绕过供应商权限——能读到什么，取决于登录账号本身的权限

采集完成后会在报告里给出「全程只读」的结论行，作为本次运行的声明。
