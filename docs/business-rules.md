# 业务规则

本文列出工具里**确定性的业务规则**——即「同样的输入必然得到同样的输出」的那部分。

> 规则来源：`statement_engine.py` 的模块文档与函数文档（从打包产物的字节码中还原）。
> 示例中的单号、料号、数量均为**虚构**。
> 本节规则可直接对应到 [../tests/test-reconciliation-rules.md](../tests/test-reconciliation-rules.md) 的测试用例。

---

## 规则总览

| # | 规则 | 语义 |
|---|---|---|
| R1 | 去重唯一键 = **单号 + 行号** | 明确禁止用「日期+料号+数量」去重 |
| R2 | 月度汇总键 = **单据日期 + 料号** | 同日同料号的数量求和 |
| R3 | 一个产品整月**只占一行** | 数量按日期摊到各日期列 |
| R4 | 日期列**只生成有业务的日** | 动态伸缩，不是固定天数 |
| R5 | 料号不在产品资料 → **明确失败** | 不允许猜，`FINAL=FAIL` |
| R6 | 缺单价 → 金额填 **0**，公式保留 | 并列入缺单价清单 |
| R7 | 单价模式 = `ZERO` / `PRODUCT_MASTER` | 两种模式二选一 |
| R8 | 表头**自动定位** | 前 N 行扫描，不写死表头行号 |
| R9 | 料号**规范化后再匹配** | 还原 Excel 的浮点料号 |
| R10 | 不调用视觉模型、不访问 ERP、不重新采集 | 生成阶段纯离线 |

---

## R1 — 去重唯一键是「单号 + 行号」

**规则**：一条送货单明细由「单据编号 + 行号」唯一确定。同一张单的第 1 行和第 2 行是两条不同记录。

**为什么不能按「日期 + 料号 + 数量」去重**：这三者相同的两条记录**是合法的**。同一天、同一个料号、同样数量，完全可能是两趟车分别送的。按内容去重会把真实的两笔合并成一笔——**少算钱**。

去重结果会记入采集/生成报告（重复行数），不是静默丢弃。

| 单号 | 行号 | 日期 | 料号 | 数量 | 判定 |
|---|---|---|---|---|---|
| SH-2026-0801 | 1 | 2026-08-03 | A100-0001 | 500 | 保留 |
| SH-2026-0801 | 2 | 2026-08-03 | A100-0001 | 500 | **保留**（不同行号） |
| SH-2026-0801 | 1 | 2026-08-03 | A100-0001 | 500 | 丢弃（单号+行号重复） |

> 第三行是同一张单同一行的重复抓取——这才是真正的重复。

## R2 — 月度汇总键是「单据日期 + 料号」

**规则**：把去重后的明细按「单据日期 + 料号」分组，数量求和。

**语义**：同一天对同一料号的多笔送货，合并成该日期列下的一个数字。

| 日期 | 料号 | 数量 | 汇总后 |
|---|---|---|---|
| 2026-08-03 | A100-0001 | 500 | 当天该料号 = 1200 |
| 2026-08-03 | A100-0001 | 700 | ↑ |
| 2026-08-05 | A100-0001 | 300 | 2026-08-05 该料号 = 300 |

注意汇总键是**单据日期**而不是「创建时间」或「导入时间」——业务上算的是送货那天的账。

## R3 / R4 — 一个产品一行，日期列动态生成

**规则 R3**：一个料号整月只出现一次，占一行。

**规则 R4**：日期列只为**当月实际有业务的日子**生成，不是固定 30/31 列。

示意（虚构）：

```
        │ 序号 │ 项目 │ 名称        │ 规格      │ 单位 │ 08-03 │ 08-05 │ ... │ 小计 │ 单价  │ 金额
────────┼──────┼──────┼─────────────┼───────────┼──────┼───────┼───────┼─────┼──────┼───────┼───────
        │  1   │ D21  │ 支架（示例） │ SPEC-0001 │  件  │ 1200  │  300  │ ... │ 1500 │ 1.20  │ 1800
```

母版里预置固定数量的日期列，实际按需插入或复用，**并复制母版的日期列样式**——所以样式和客户要求的一致，不需要人工调格式。

实现上由 `_insert_date_cols()` 完成：在指定列之前插入 N 列，样式从模板日期列复制。

**为什么要动态**：固定 31 列的母版打印出来一大片空白，客户不接受。日期列跟着业务走，表格才紧凑。

## R5 — 料号不在产品资料里，就明确失败

**规则**（模块文档原文）：

```
料号不存在于产品基础资料 -> 明确异常, 不允许猜, FINAL=FAIL
```

**为什么这么严**：如果允许「猜」——比如按名称相似度匹配一个料号——那么猜错时产出的是一份**看起来正常但对不上账**的对账单。这种错误交到客户手里比直接失败严重得多。

所以：料号对不上，整份对账单判定失败，并列出是哪些料号缺失。人补齐产品资料后重跑。

---

## R6 / R7 — 单价的两种模式与「缺单价填 0」

**两种单价模式**（配置项 `_price_mode`）：

| 模式 | 语义 |
|---|---|
| `ZERO` | 单价全部填 0，**金额公式保留** |
| `PRODUCT_MASTER` | 从产品资料的「单价（未税）」列读取；**缺单价自动填 0** |

`ZERO` 模式用于「先把数量对上，价格以后再算」的场景——公式在，数据齐了直接出金额。

**缺单价的行为**：填 0，但**记入缺单价清单**（`build_workbook` 的返回值之一），报告里能查到是哪几个料号。

这样「缺数据」表现为「金额为 0 + 有清单」，而不是「金额算错」。人补完单价重跑一次即可。

## R8 — 表头自动定位

**规则**：在数据表的前若干行内扫描，识别出表头行，建立「字段 → 列号」映射。

**为什么要这样**：母版顶部往往有标题行、购方名称行等，真正的表头不在第一行；而且客户调整一次版式，写死行号的代码就废了。

实现：`_detect_header(ws, scan_rows)` → `(行号, {字段: 列号})`；配合 `_norm_header()` 做文本规范化（去空白、统一括号、转小写），避免因空格或全半角差异匹配失败。

---

## R9 — 料号规范化

**规则**：匹配前先规范化料号。其中最关键的一条：**Excel 常把纯数字料号存成浮点数**。

```
Excel 里看到的    读出来是        规范化后
9000000001    →   9000000001.0  →  9000000001
```

如果不处理，`9000000001`（产品资料里）和 `9000000001.0`（从 Excel 读的）就是两个不同的字符串，匹配必然失败，然后触发 R5 的明确失败。

（上面是**虚构**的示例料号，仅用于说明格式问题。）

这是被真实数据教出来的规则：**料号在业务上是字符串，不是数字。** 只要参与过比较，就不能让它经过浮点数。

`norm_price()` 同理：无法解析成数字的单价返回 `None`，不抛异常，交由「缺单价填 0」规则处理。

---

## R10 — 生成阶段是纯离线的

**规则**（模块文档原文）：

```
- 不调用视觉模型、不访问 ERP、不重新采集;
```

生成阶段只读本地产物（CSV、产品资料、母版），不产生任何外部访问。带来的好处：

- **可重复**：同一份输入，任何时候跑结果都一样
- **可审查**：出问题时不需要重现「当时的 ERP 状态」
- **快**：不用等网络

采集与生成分成两个阶段、两个模块，正是为了这条规则——采集可以失败重试，生成必须确定性。

## 质检项

生成结束后跑一批检查，每项带 `fatal` 标记：

| 检查方向 | 说明 | 不过时 |
|---|---|---|
| 数量守恒 | 写入表格的数量合计 = 去重后明细的数量合计 | fatal |
| 料号覆盖 | 每个明细料号都在表里有一行 | fatal |
| 合计一致 | 小计与金额列的公式结果自洽 | 视项而定 |
| 日期列一致 | 日期列与实际有业务的日期集合一致 | 视项而定 |
| 来源行数 | 明细行数、去重后行数、重复行数的关系明确 | 视项而定 |

fatal 项不过 → 整份对账单判定失败；非 fatal 项只记录偏差，交人判断。

其中「来源行数」这条尤其重要：它把 `源行数 = 去重后行数 + 重复行数` 这个恒等式显式检查一遍。
**只有当账目能对上，才允许它被交出去。**
