# 业务规则测试用例

本文把 [../docs/business-rules.md](../docs/business-rules.md) 的规则写成**可验证的用例**。

> **说明**：本仓库只有打包产物与源码，没有原始测试套件，也**没有可运行的实现**。
> 因此这里给出的是**行为规格（specification）**，不是「已通过的测试结果」。
> 每条用例都写明：输入、期望、以及**为什么这么期望**。
> 任何实现都可以拿这些用例来验证自己是否符合规则。

编号与 `business-rules.md` 的 R1–R10 一一对应。

---

## R1 — 去重唯一键 = 单号 + 行号

### T1.1 同单同行完全重复 → 只留一条

```yaml
输入:
  - {单号: SH-001, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
  - {单号: SH-001, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
期望:
  去重后 1 条
  重复计数 = 1
理由: 这是真正的重复（同一张单的同一行被抓了两次）
```

### T1.2 同单不同行 → 两条都保留 ⭐

```yaml
输入:
  - {单号: SH-001, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
  - {单号: SH-001, 行号: 2, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
期望:
  去重后 2 条
  重复计数 = 0
理由: 行号不同就是两条明细。这是本规则存在的全部意义
```

### T1.3 三者全同但单号不同 → 两条都保留 ⭐

```yaml
输入:
  - {单号: SH-001, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
  - {单号: SH-002, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
期望:
  去重后 2 条
理由: 两趟车分别送的，日期/料号/数量巧合相同。
      ★ 如果实现用「日期+料号+数量」去重，这条会失败——这正是规则禁止那种做法的原因
```

## R2 — 月度汇总键 = 单据日期 + 料号

### T2.1 同日同料号多笔 → 求和

```yaml
输入:
  - {单号: SH-001, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
  - {单号: SH-002, 行号: 1, 日期: 2026-08-03, 料号: DEMO-1001, 数量: 700}
期望:
  2026-08-03 × DEMO-1001 = 1200
理由: 同一天对同一料号的数量合并为当天该料号的一个数字
```

### T2.2 不同日期同料号 → 分列，不合并

```yaml
输入:
  - {日期: 2026-08-03, 料号: DEMO-1001, 数量: 500}
  - {日期: 2026-08-05, 料号: DEMO-1001, 数量: 300}
期望:
  08-03 列 = 500，08-05 列 = 300（两个不同的日期列）
理由: 汇总键是「单据日期 + 料号」，日期不同就是不同的格子
```

### T2.3 汇总用的是「单据日期」而非导入/创建时间

```yaml
输入: 一条 单据日期=2026-08-03 但系统创建时间=2026-08-07 的记录
期望: 归入 08-03
理由: 业务上算的是送货那天的账
```

## R3 / R4 — 一个产品一行，日期列只生成有业务的日

### T3.1 同一料号整月只出现一行

```yaml
输入: DEMO-1001 在 08-03、08-05、08-11 各有多笔
期望:
  输出表中 DEMO-1001 只有一行
  三个日期的数量分别落在对应日期列
```

### T4.1 日期列数量 = 当月实际有业务的日期数

```yaml
输入: 当月只有 08-03、08-05、08-11 三天有业务
期望:
  日期列恰好 3 列（不是 31 列）
  列顺序按日期升序
理由: 固定 31 列打印出来一大片空白，客户不接受
```

### T4.2 无业务的日期不生成列

```yaml
输入: 08-04 没有记录
期望: 不存在 08-04 列（而不是生成一列全 0）
```

## R5 — 料号不在产品资料里 → 明确失败

### T5.1 未知料号 → 整体 FAIL ⭐

```yaml
输入:
  明细含料号 DEMO-9999，产品资料中没有
期望:
  最终状态 = FAIL
  报告列出缺失料号 [DEMO-9999]
理由: 模块文档原文「料号不存在于产品基础资料 -> 明确异常, 不允许猜, FINAL=FAIL」
```

### T5.2 不得用相似料号顶替 ⭐

```yaml
输入:
  明细含 DEMO-100X，产品资料中只有 DEMO-1001
期望:
  FAIL，且**不得**匹配到 DEMO-1001
理由: 「不允许猜」。猜对一次不会被发现，猜错一次就是给客户的账目出错
```

## R6 / R7 — 单价模式与缺单价

### T6.1 缺单价 → 金额填 0，并进清单

```yaml
输入: DEMO-1005 在产品资料中单价为空，明细中有它的数量
期望:
  单价列 = 0
  金额 = 0
  缺单价清单包含 DEMO-1005
理由: 让「缺数据」表现为「0 + 有清单」，而不是「金额算错」
```

### T7.1 ZERO 模式 → 单价全 0，公式保留

```yaml
输入: price_mode = ZERO
期望:
  所有单价 = 0
  金额单元格仍然是公式（而非写死的 0）
理由: 数据补齐后公式直接出金额，不用重新生成表
```

### T7.2 PRODUCT_MASTER 模式 → 从产品资料读单价

```yaml
输入: price_mode = PRODUCT_MASTER，DEMO-1001 单价 1.20，数量 1500
期望: 金额 = 1800.00
```

## R8 — 表头自动定位

### T8.1 表头不在第一行

```yaml
输入:
  第 1 行 标题、第 2 行 购方名称、第 3 行 才是表头
期望:
  正确识别第 3 行为表头并建立列映射
理由: 母版顶部有标题行，写死「表头在第 1 行」的代码会直接错位
```

### T8.2 表头文本含多余空格 / 全半角差异

```yaml
输入: 表头写作 "  单价 （未税） " 或 "单价(未税)"
期望:
  都能匹配到「单价」字段
理由: _norm_header 做去空白、括号统一、小写
```

## R9 — 料号规范化

### T9.1 浮点料号必须还原成整数串 ⭐

```yaml
输入:
  产品资料里的料号为 9000000001（文本，虚构示例）
  从 Excel 读出的料号为 9000000001.0（浮点）
期望:
  两者匹配成功
理由: Excel 常把纯数字料号存成 float。不处理就会匹配失败并触发 R5 的 FAIL
```

### T9.2 前导零不得丢失

```yaml
输入: 料号 "0012345"（文本，含前导零）
期望:
  规范化后仍为 "0012345"，不得变成 12345 或 12345.0
理由: 料号在业务上是字符串，不是数字
```

### T9.3 单价无法解析 → 返回 None，不抛异常

```yaml
输入: 单价单元格为 "待定" 或空
期望:
  norm_price 返回 None
  后续按 R6「缺单价填 0」处理，不中断生成
```

## R10 — 生成阶段纯离线

### T10.1 生成不访问 ERP、不重新采集

```yaml
输入: 已有 CSV + 产品资料 + 母版
期望:
  生成过程不产生任何网络请求
  重复运行两次，输出内容完全一致
理由: 模块文档原文「不调用视觉模型、不访问 ERP、不重新采集」
```

### T10.2 输出可复现

```yaml
输入: 同一份输入跑两次
期望:
  两次的对账单数据区完全一致
理由: 确定性是「结果可被审查」的前提
```

## 质检项（对应 business-rules.md「质检项」）

### TQ.1 数量守恒（fatal）

```yaml
输入: 去重后明细数量合计 = 12,345
期望:
  写入表格的数量合计 = 12,345
  不等 → FAIL
```

### TQ.2 料号覆盖（fatal）

```yaml
输入: 明细涉及 6 个料号
期望:
  输出表中有 6 个产品行
  缺任一 → FAIL
```

### TQ.3 来源行数恒等式

```yaml
输入: 源行数 43，重复 1
期望:
  去重后行数 = 42
  43 = 42 + 1 成立，报告写明这三个数
理由: 让「少了几行」这件事在报告里看得见，而不是等到客户发现
```

### TQ.4 fatal 与非 fatal 的区分

```yaml
输入: 一个 fatal 项不过 + 若干非 fatal 项有偏差
期望:
  最终状态 FAIL（fatal 一票否决）
  报告仍列出非 fatal 项的偏差明细供人判断
```

## 关于本文件的性质

再次强调：**这些是规格，不是测试结果。**

原工具没有随包提供测试套件，本仓库也没有可运行的实现，所以无法声称「这些用例已通过」。
它们的作用是：

1. 把口头规则变成**可证伪**的断言
2. 让任何实现（包括未来重写的版本）有明确的验收标准
3. 让「哪些行为是刻意设计的」有据可查
